High-concurrency backend 2026 · solo · live
Node.jsPostgreSQL 17Kafka 3.9 (KRaft)RedisDocker

TicketFlow

A ticket-booking backend built around a single promise: the same seat never gets sold twice, no matter how many people tap "book" in the same millisecond. Two-phase hold → pay → confirm, with a five-minute hold that expires whether or not anyone is watching.

Load test: 20 simultaneous requests on one seat → 1 booking, 19 rejections, 0 oversells. Deadlock-free across multi-seat orders.

Live demo Source
› Read the engineering notes
How it works
  • Pessimistic (SELECT … FOR UPDATE) and optimistic (version CAS) locking are exposed as separate endpoints so the two strategies can be benchmarked against the same workload.
  • Multi-seat orders acquire row locks in ascending seat order, with a retry on Postgres 40P01 — that ordering is what makes deadlock impossible rather than unlikely.
  • Holds expire two ways: lazily on read, and via a background sweeper, so an idle system still releases inventory.
The hard parts
  • Kafka publishes after commit and consumers dedupe against a processed_messages table using the unique-violation code 23505 — at-least-once delivery plus consumer idempotency.
  • Redis serves seat-availability reads cache-aside, but booking correctness is never delegated to the cache: the Postgres row lock stays the source of truth.
  • A streaming read replica takes read traffic, with ?fresh=1 to force read-your-writes when a user needs to see their own booking immediately.
What I don't claim
  • It's effectively-once, not exactly-once. A duplicate can be delivered; it just can't be processed twice.
  • Redis, Kafka and the replica are all optional — the system degrades to plain Postgres if any of them are down, which is honest engineering but also means the free-tier demo isn't exercising them.
Event-sourced banking core 2026 · solo
Node.jsExpressPostgreSQLDocker

The Ledger

A double-entry ledger where balances aren't stored — they're derived. Every movement of money is an append-only event; the balance is what you get when you replay the tape. Snapshots exist, but only ever as a cache, never as the truth.

10-way concurrent withdrawal test passes; zero-sum invariant holds across the full event history after every run.

Source
› Read the engineering notes
Decisions I'd defend
  • Money is stored as integer paise. No float ever touches a balance.
  • Thin API, fat core: HTTP handlers do validation and nothing else; every accounting rule lives in a layer that doesn't know what a request is.
  • Accounts are locked in sorted order on every transfer, which removes the classic A→B / B→A deadlock.
A bug worth the story
  • Replay ordering was originally by timestamp. It broke: Postgres stores microseconds, JavaScript rounds to milliseconds, so two events written in the same millisecond could replay in either order — and a withdraw-then-deposit could silently become deposit-then-withdraw.
  • Fix: order on the monotonic entry ID, not the clock. Also fixed a BIGSERIAL sequence collision caused by manually seeding rows past the sequence value.
What I don't claim
  • Single-node Postgres. There's no distributed consensus here and I wouldn't pretend the design survives being sharded without rework.

CodeSync

A browser IDE where several people edit the same file and run it in four languages. The interesting half isn't the editor — it's the sandbox: every run gets a throwaway container with no network, capped memory and a hard timeout, because "run arbitrary user code" is a security problem wearing a feature's clothes.

Per-run container: no network, 256 MB, 0.5 CPU, read-only mount, 20-second kill. JS, Python, C++, Java.

Source
› Read the engineering notes
How it works
  • Monaco emits deltas over Socket.IO; a suppress flag on the receiving side stops an applied remote edit from being re-broadcast as a local one, which is what otherwise turns two editors into an infinite loop.
  • Rooms get isolated workspaces behind a join key, with an 800 ms debounced auto-save so a dropped tab doesn't lose work.
  • JWT + bcrypt auth on the Express REST layer; the socket layer only trusts a verified session.
A pivot I'd explain
  • I wanted a real PTY via node-pty and lost days to native build failures (posix_spawnp under newer Node on macOS). I pivoted to child_process rather than keep sinking time into the toolchain — a tradeoff that cost a feature and saved the project.
What I don't claim
  • Sync is a relay, not CRDT or OT. Two people typing at the same offset in the same instant can diverge. I know exactly why, and OT is the upgrade path — but today it's a limitation, not a solved problem.
  • Output is buffered and pushed after the process exits, not streamed live. Moving exec → spawn is the fix.
M.Tech thesis · applied ML 2026 · ongoing
PythonXGBoostscikit-learnSHAPSMOTE

Intrusion detection for Industrial IoT — and the accuracy that was a lie

A 15-class attack classifier on the Edge-IIoTset dataset. The headline isn't the score; it's that the first score was 99.99% and I didn't believe it. SHAP showed why: three features were encoding artefacts that leaked the label, and the model was reading them instead of the traffic.

After the audit: 99.36% binary / 91.44% multi-class, on 20 features instead of 39, with 6 shortcut features identified and handled.

Source
› Read the engineering notes
The method
  • The contribution isn't "remove suspicious features". It's a diagnostic that classifies why a feature looks too good: encoding-induced (fix the parse), structural (drop it), or genuinely dominant signal (keep it and say so).
  • Two kinds of leakage are kept separate throughout: evaluation leakage, where test data bleeds into feature selection during cross-validation, and dataset leakage, where a feature is a label shortcut. Prior work often conflates them.
Why it matters
  • An IDS that scores 99.99% in a paper and fails in a plant is worse than one that honestly scores 91%. The audit turns an unusable number into a defensible one.
  • SMOTE handles the long tail of rare attack classes; the feature cut from 39 → 20 also makes the model cheap enough to sit near the edge.
What I don't claim
  • Single dataset, single environment. Cross-dataset generalisation is untested.
  • A deep-learning baseline was dropped after a Python 3.14 / TensorFlow incompatibility, so the comparison is tree-and-kernel models only.

Hybrid Search RAG Pipeline

A retrieval-augmented generation pipeline written without a framework, so every stage is inspectable: chunking, dense embeddings, BM25, reciprocal rank fusion, then a local model that has to answer from the retrieved text or say it can't. No LangChain, no black box.

Ships with its own evaluation suite — Hit Rate, Recall@k, Precision@k, MRR — so retrieval changes are measured, not vibed.

Source
› Read the engineering notes
The pipeline
  • all-MiniLM-L6-v2 (384-dim) into FAISS for dense retrieval, rank_bm25 for lexical, fused with RRF at k=60.
  • FastAPI exposes /search, /ask and /health, with the chat frontend served same-origin so there's no CORS theatre in a demo.
  • Generation runs locally on Ollama (llama3.2) and is grounded — out-of-corpus questions were tested and do get refused.
The result I didn't expect
  • On my test set, dense-only retrieval beat the hybrid. That's the honest finding, and it's reported rather than buried.
  • The reason is the query mix: my questions were paraphrase-heavy, which is exactly where BM25 has nothing to contribute. Fusion earns its keep when queries carry rare literal tokens — IDs, error codes, product names.
  • That's the actual lesson of the project: retrieval strategy is a function of your query distribution, and you only find that out by measuring.
What I don't claim
  • Small corpus, single-machine index. Nothing here has been tested at a scale where FAISS index type and sharding start to matter.
Microservices platform 2025 · solo
Node.jsReactMongoDBRedisNginxDocker

MediCore

A hospital management platform split into five Dockerized services — patients, appointments, records, auth, gateway — behind Nginx, with JWT carried across service boundaries. Built to learn where microservices actually help and where they just add a network hop.

Redis cache-aside on the read-heavy paths: 120 ms → 45 ms median read latency, ~40% fewer reads reaching MongoDB.

Source
› Read the engineering notes
How it's put together
  • Each service owns its own data and talks over HTTP through the gateway; no service reaches into another's database.
  • Nginx handles routing and TLS termination; auth issues the token, every other service only verifies it.
  • Cache-aside with explicit invalidation on write, rather than a TTL guess — stale medical records are not an acceptable failure mode.
What I don't claim
  • Five services is more architecture than this domain needs. The honest verdict from building it: the split bought me isolation and cost me debugging time, and I'd start with a modular monolith next time.
  • No service mesh, no distributed tracing. Cross-service failures are debugged by reading logs.
Encrypted messaging 2025 · solo
Node.jsSocket.IOMongoDBAES-256-GCM

PQC SecureChat

A real-time chat app built on a KEM-DEM envelope: a per-message symmetric key, wrapped for the recipient, with the payload sealed under AES-256-GCM. The server stores and routes ciphertext and never holds anything it could decrypt.

Source
› Read the engineering notes
The idea
  • GCM gives authenticated encryption, so a tampered message fails to open rather than decrypting to garbage.
  • The envelope structure is the point: it's the shape real post-quantum schemes use, which makes the key-exchange step swappable later.
What I don't claim
  • This is not post-quantum. It borrows the KEM-DEM structure that PQC standards use; it does not implement a lattice-based key exchange. Calling it PQC would be a lie and the name is the weakest thing about the project.

How it works

What I found reviewing my own code

Research

M.Tech thesis, IIIT Allahabad. Currently being written up for submission.

A SHAP-driven leakage audit for IIoT intrusion detection

Published intrusion-detection results on IIoT benchmarks routinely report near-perfect accuracy. My thesis argues that a large share of those numbers are artefacts — the model has found a shortcut in how the dataset was encoded, not a pattern in the attack.

The method uses SHAP attributions as a diagnostic rather than a post-hoc explanation: features that dominate suspiciously are traced back to a root cause and sorted into three buckets — encoding-induced, which gets a canonical parse fix; structural, which gets dropped; and genuine dominant signal, which stays and gets justified. That distinction is the contribution. Prior work tends to delete anything that looks too predictive, which throws away real signal along with the leak.

It also keeps two things separate that the literature often blurs: evaluation leakage, where test data influences feature selection during cross-validation, and dataset leakage, where a feature is effectively a copy of the label.
